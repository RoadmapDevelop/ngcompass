## Package 1: `@ngcompass/common`

**Score: 7.2 / 10**

### What Was Evaluated
`src/types.ts`, `src/errors.ts`, `src/interfaces.ts`, `src/logger.ts`, `src/utils/locator.ts`, `src/utils/stable-serialize.ts`

### Strengths
- `Result<T, E>` functional error type is clean and correct.
- `InfrastructureErrorCollector` pattern is excellent — accumulates errors without interrupting the pipeline, with proper phase tagging.
- `AnalyzerError` hierarchy (base → `ConfigurationError`, `ParseError`, `RuleError`, `RuleExecutionError`) is clean, each adds contextual fields.
- Logger uses namespace filtering with compile-time guard (`satisfies Namespace[]`) — very well designed.
- All public types use `readonly` consistently.

### Issues Found

#### Duplicate / Overlapping Definitions
- `RulePlugin`, `RegisterOptions`, `RuleRegistry` are defined in **both** `common/src/types.ts` (lines 205–227) **and** `rules/src/registry/rule-registry.ts`. The `common` version uses `any` for `handler` — it is a weaker, shadow duplicate.
- `AnalyzerConfig` and `NormalizedAnalyzerConfig` both exist in `interfaces.ts`; `NormalizedAnalyzerConfig` is not generated by transforming `AnalyzerConfig` at the type level — it is manually redeclared with half the fields changed, prone to drift.

#### Weak Typing
- `RuleRegistry` interface in `types.ts` uses `any` for `get()`, `getAll()`, `handler` — defeats TypeScript's value in this shared foundation package.
- `RuleContext.template?: any` and `RuleContext.style?: any` — untyped AST nodes leak `any` into every rule handler.
- `HealthReport.config?: any` in `interfaces.ts` — no schema information.
- `ConfigIssue` fields (`code`, `message`, `path`, etc.) are **not** `readonly` — inconsistent with the rest of the codebase.

#### Severity Type Design
- `Severity` union: `'critical' | 'high' | 'moderate' | 'low' | 'info' | 'warning' | 'error' | 'hint'` mixes ESLint-style values (`'warning'`, `'error'`) with a custom scale (`'critical'`, `'high'`). This creates ambiguity — `'error'` and `'critical'` map to different things in reporters.

#### Logger
- `logger.ts` initialises from `process.env.DEBUG` at module load time — makes it untestable without env-var patching. No `reset()` or factory method for tests.
- `logLevel` parameter in `log()` is named `_level` and never used — dead parameter (logged always to stderr regardless of level).

#### Deprecated Field
- `RuleContext.sourceFile?: import('typescript').SourceFile` is marked `// Deprecated` but never removed — dead field increases cognitive load for rule authors.

### Suggestions
1. Remove `RulePlugin`, `RegisterOptions`, `RuleRegistry` from `types.ts` — they should live only in `@ngcompass/rules` and be imported by `common` if needed, not duplicated.
2. Replace `any` with proper generic types in `RuleRegistry` interface.
3. Type `RuleContext.template` and `RuleContext.style` with proper AST node types from `@ngcompass/ast`.
4. Remove the deprecated `sourceFile` field from `RuleContext`.
5. Add `readonly` to all `ConfigIssue` and `HealthReport` fields.
6. Export a `createLogger()` factory from `logger.ts` for test isolation.

## Package 2: `@ngcompass/ast`

**Score: 8.1 / 10**

### What Was Evaluated
`src/ast/matchers.ts`, `src/ast/types.ts`, `src/analyzers/component-analyzer.ts`, `src/analyzers/template-analyzer.ts`, `src/visitor.ts`, `src/node-streams.ts`, `src/parsers/ts.ts`, `src/parsers/html.ts`

### Strengths
- Iterative DFS walker in `visitor.ts` — avoids stack overflow on deep ASTs. Excellent engineering decision.
- Tri-state metadata pattern (`LiteralValue | NonLiteralValue | MissingValue`) with pre-allocated singletons is a clean, zero-allocation design.
- `WeakMap`-based component cache in `analyzeComponent()` is O(1) after first call and GC-friendly.
- `matchers.ts` is well-named and scoped — pure functions, zero allocation, early returns.
- `resetComponentCacheStats()` / `getComponentCacheStats()` allows performance monitoring without mutable globals.

### Issues Found

#### `any` in Private Extractors
- All private extractor functions in `component-analyzer.ts` accept `metadataObject: any` (lines 198, 208, 232, 242, 252, 262) — the public `analyzeComponent` correctly types its input, but the private helpers lose that guarantee entirely. Type assertions inside them (`cdNode as any`) compound this.

#### Fragile String Splitting
- `extractRenames()` (line 316): `value.split(':').map(s => s.trim())` will silently truncate rename strings with more than one colon — no validation or error.
- No guard for the case where `parts.length !== 2` after splitting.

#### Unsafe Type Casts in Matchers
- `matchers.ts` line 71: `const prop = (callee as MemberExpression).property` — cast without prior type narrowing that the callee actually conforms to `MemberExpression` beyond `expr.type` check.
- `getKeyNameUnsafe` casts `key as StringLiteral` without verifying `lit.value` is actually a string until the next line — the check does happen, but the cast precedes it.

#### Missed `Unsafe` Pattern Opportunity
- `isInputSignal()` and `getInputSignalAliasUnsafe()` differ in naming convention but both can return falsy — `isInputSignal` returns `false`, `getInputSignalAliasUnsafe` returns `undefined`. A caller expecting consistent `Unsafe` naming would be confused by the boolean-returning sibling.

### Suggestions
1. Type private extractor parameters with the correct `ObjectExpression` type instead of `any`.
2. Add validation to `extractRenames` for multi-colon strings and return `null` on invalid input.
3. Move `isInputSignal` to follow the same naming convention as other matchers, or document the intentional boolean return.

## Package 3: `@ngcompass/cache`

**Score: 6.8 / 10**

### What Was Evaluated
`src/services/result-cache.ts`, `src/drivers/atomic.ts`, `src/drivers/memory.ts`, `src/drivers/disk.ts`, `src/drivers/json-file.ts`, `src/utils/stable-serialize.ts`, `src/env-fingerprint.ts`

### Strengths
- `atomic.ts` handles the catalog-init race condition correctly with the generation-guard pattern — production-grade concurrency handling.
- `hasMany()` short-circuits on empty cache directory, preventing thousands of unnecessary `fs.access` calls.
- Descriptive comments in `atomic.ts` explain every intentional no-op catch block.
- Driver interface abstraction (`AsyncDriver<T>`) is clean and swappable.
- Self-healing cache corruption (delete bad entry → cold rebuild) in `tryLoadPlanFromCache`.

### Issues Found

#### Magic Numbers — `result-cache.ts`
- `BATCH_SIZE = 200` appears as a **local constant** in three separate function scopes (lines 143, 199, 239) — should be a single named module-level constant.
- `METADATA_BATCH_SIZE = 100` (line 261) is inconsistently named compared to `BATCH_SIZE`. No explanation of why the two values differ.

#### Metadata Key Collision Risk — `result-cache.ts`
- `metadataDriver = driver` — **the same driver instance** is used for both result data and metadata. The key `${hash}.meta` is used to distinguish them, but if a rule ever produces a task ID ending in `.meta`, data and metadata entries would collide. No guard exists.

#### Logic Duplication — `result-cache.ts`
- The hit-counting logic inside `getManyWithMetadata` (lines 246–252) duplicates the `incrementHits()` function directly — it manually computes `hits + 1` and `lastAccess: Date.now()` instead of calling `incrementHits()`. This will diverge on future changes.
- `getOrCreateMetadata()` is called on every `set()` to pre-create metadata, even when the metadata is never read. Creates unnecessary write overhead for large batch sets.

#### Silent Error Swallowing
- `incrementHits(hash).catch(() => {})` in `get()` and `getMany()` silently discards metadata update failures with no logging — makes debugging impossible.

#### `json-file.ts` Missing Validation
- `JSON.parse()` result is cast directly to `T` with no schema validation — corrupt entries silently become valid objects.
- No file size limit — a malformed large file would be fully loaded into memory before failing.

### Suggestions
1. Extract `BATCH_SIZE = 200` and `METADATA_BATCH_SIZE = 100` to named module-level constants with a comment explaining the values.
2. Use separate driver instances (or separate key namespaces) for data and metadata to eliminate collision risk.
3. Replace the inline hit-counting logic in `getManyWithMetadata` with a call to `incrementHits()`.
4. Replace `.catch(() => {})` with `.catch(err => debug('cache', ...))` at minimum.

## Package 6: `@ngcompass/planner`

**Score: 6.5 / 10**

### What Was Evaluated
`src/builder.ts`, `src/types.ts`, `src/task-builder.ts`, `src/hashing.ts`, `src/indexes.ts`, `src/incremental.ts`, `src/serialize.ts`, `src/worker.ts`, `src/utils.ts`

### Strengths
- `types.ts` is exceptionally well-documented — every interface, field, and phase is explained. Phase markers (`@since Phase 1.75`) are useful for tracing history.
- Content-addressed task IDs (SHA-256 of inputs + options) are the correct approach for precise cache invalidation.
- Plan deserialization handles corruption gracefully — deletes bad entry and triggers cold rebuild.
- `ExecutionIndexes` pre-computation (O(1) queries later) is a smart performance investment.

### Issues Found

#### Pervasive `any` Type Abuse — `builder.ts`
- `validateBuildInputs(files, rules: ReadonlyMap<string, any>)` — `any` for `rules` loses all type information.
- `collectApplicableRulesFromTasks(tasks, rules: ReadonlyMap<string, any>): any[]` — both parameter and return type are `any`.
- `calculateHashFromTasks(tasks, applicableRules: any[])` — `any[]`.
- `convertTasksToPlan(tasks, rules: ReadonlyMap<string, any>)` — `any`.
- These functions should use `ResolvedRule` from `@ngcompass/common`.

#### Magic Numbers in Function Body
- `buildAllTasks()` line 379: `const PARALLEL_THRESHOLD = 10000` and line 380: `const WORKER_COUNT = 4` — magic numbers defined inside a function body. They should be module-level named constants or derived from `ExecutionPlanOptions`.

#### Unsafe Cast for Precomputed Analysis
- `tryLoadPlanFromCache()` line 257: `precomputedAnalysis: precomputedAnalysis as any` and line 257: `} as unknown as ExecutionPlanOutput` — double unsafe cast to work around an incomplete inline object literal missing required `ExecutionIndexes` fields. Should construct a proper `ExecutionPlanOutput` object or use a factory.

#### Duplicated `resolveWorkerPath()`
- `builder.ts` lines 459–483 defines `resolveWorkerPath()` which is **identical in purpose and nearly identical in code** to `resolveWorkerPath()` in `engine/src/worker-pool.ts` (lines 187–208). Two packages independently re-implement the same file path resolution logic — should live in a shared utility.

### Suggestions
1. Replace all `any` in `builder.ts` with `ResolvedRule` from `@ngcompass/common`.
2. Move `PARALLEL_THRESHOLD` and `WORKER_COUNT` to module-level named constants.
3. Replace the `as unknown as ExecutionPlanOutput` cast with a proper factory function.
4. Extract `resolveWorkerPath()` to a shared internal utility in `@ngcompass/common` or a new `@ngcompass/internal-utils` package.

## Package 7: `@ngcompass/engine`

**Score: 6.0 / 10**

### What Was Evaluated
`src/orchestrator.ts`, `src/single-pass-engine.ts`, `src/worker-pool.ts`, `src/visitor-registry.ts`, `src/runner.ts`, `src/execution-worker.ts`, `src/analysis-context.ts`, `src/analysis-stats.ts`, `src/spinner.ts`, `src/constants.ts`

### Strengths
- `orchestrator.ts` is clean and well-structured — clear short-circuit for precomputed analysis, good separation of executed vs skipped tasks.
- `single-pass-engine.ts` correctly implements O(N) traversal with O(1) dispatch — the VisitorMap pattern is excellent.
- Performance budget enforcement (2ms / 5ms p95) is a thoughtful quality gate.
- `distributeTasks()` using greedy LPT (Longest Processing Time first) partition is the correct algorithm for worker load balancing.
- `retrieveSkippedResults()` checks pre-loaded `cachedResults` before hitting the cache service — correct optimization.

### Issues Found

#### Spinner Class Duplication — `worker-pool.ts`
- `worker-pool.ts` lines 13–46 contains an **inline `Spinner` class** that is **identical** to `src/spinner.ts`. Two copies of the same class in the same package — one is never used by the other. Clear copy-paste that was never cleaned up.

#### `runLocalFallback()` Hardcoded Concurrency
- `worker-pool.ts` line 166: `const limit = pLimit(4)` — hardcoded to 4 regardless of the configured `maxWorkers` or the `LOCAL_CONCURRENCY_LIMIT` constant defined in `constants.ts`. The orchestrator goes to great lengths to compute `effectiveMaxWorkers`, but the fallback path ignores it entirely.

#### Worker Exit Race Condition
- In `worker-pool.ts`, a worker's `exit` event handler rejects the promise if the exit code is non-zero — but if the `message` event fires first (resolve), and then `exit` fires with code 0, nothing happens. However, if `exit` fires before `message` with code 0, neither resolve nor reject is called, causing a hanging promise. The `exit` handler should only act on non-zero codes **and** only if the promise hasn't already settled.

#### `error` and `warn` Name Shadowing
- `worker-pool.ts` line 2: `import { warn, error } from "node:console"` — imports Node's console functions as module-level names `warn` and `error`. These shadow any future imports of the project's own `warn`/`error` logger functions and are confusing to readers.

#### Imports Without `.js` Extension
- `worker-pool.ts` lines 3–7 use imports without `.js` extension (e.g., `"./analysis-context"`, `"./runner"`) — inconsistent with `orchestrator.ts` which correctly uses `.js` extensions. This will break ESM resolution in production builds.

### Suggestions
1. Delete the inline `Spinner` class from `worker-pool.ts` and import from `./spinner.js`.
2. Pass the configured `concurrency` value to `pLimit()` in `runLocalFallback()`.
3. Fix the worker exit race condition with a settled-flag.
4. Rename the `node:console` imports to `consoleWarn`, `consoleError` to avoid shadowing.
5. Add `.js` extensions to all relative imports in `worker-pool.ts`.

3. Delete `rules/src/visitor.ts` and import from `@ngcompass/ast`.
4. Remove `allowOverride: true` from `adapter.ts` — built-in rules should never silently override each other.

## Package 9: `@ngcompass/reporters`

**Score: 7.8 / 10**

### What Was Evaluated
`src/reporters/console-reporter.ts`, `src/reporters/json-reporter.ts`, `src/factory.ts`, `src/output.ts`, `src/severity-utils.ts`, `src/code-frame.ts`

### Strengths
- `ConsoleReporter` follows Command-Query Separation well — pure data functions (`countSeverities`, `buildCompactFailureLine`, `buildCardHeader`) are separated from rendering commands.
- Named constants replace magic literals (`TYPE_WIDTH_ERROR = 5`, `TYPE_WIDTH_WARNING = 7`, `STACK_HEADER_LINE_SKIP = 1`, `TRAILING_PERIOD_RE`).
- `FailureCard` DTO pattern cleanly separates pre-computation from rendering.
- Source reader injection (`SourceReader = defaultSourceReader`) makes the reporter testable without filesystem access.
- `cwd` injection avoids `process.cwd()` side-channel in render path.
- `summary()` method is intentionally a no-op with an explicit comment — honest design.

### Issues Found

#### O(n²) Array Allocation in `groupFailuresByFile`
- Lines 110–114: Uses `reduce` with `[...existing, failure]` — creates a new array on **every failure** processed. For 1,000 failures in one file, this allocates 1,000 intermediate arrays. Should use `push()` into a mutable map value or `Map.set(key, [...(map.get(key) ?? []), failure])` replaced with a `get` + `push` pattern.

#### Fixed Terminal Width
- `buildIndexedSeparator()` line 61: `const FIXED_WIDTH = 160` — hardcoded 160-char separator width, regardless of actual terminal width. On narrow terminals (80 chars) this wraps; on wide terminals (240 chars) it looks narrow. Should use `process.stdout.columns ?? 80`.

#### Double `pc.dim` Call
- `buildCardMessageLine()` line 204: `pc.dim(pc.dim(failure.ruleName))` — double application of the dim style has no visual effect beyond single dim. One is redundant.

#### `extractAllFailures()` Type Assertion
- Line 348: `result.failures as RuleFailure[]` — `result.failures` is already `ReadonlyArray<RuleFailure>`, so the cast is unnecessary but implies the type might not be correct. Should use a proper spread or slice instead.

### Suggestions
1. Replace the `reduce` + spread in `groupFailuresByFile` with `get` + `push`.
2. Replace hardcoded `FIXED_WIDTH = 160` with `Math.min(process.stdout.columns ?? 80, 160)`.
3. Remove the extra `pc.dim` call on rule name.
4. Remove the unnecessary `as RuleFailure[]` cast from `extractAllFailures`.

## Cross-Package Issues

### CI-1 — Single-Pass Engine Triplicated
The single-pass AST engine is implemented in:
1. `packages/engine/src/single-pass-engine.ts` (authoritative)
2. `packages/rules/src/engine/single-pass-engine.ts` (copy, already diverged)

Both implementations have the same function signature and structure but have drifted apart. Every bug fix or enhancement must be applied twice. The `rules` copy should be deleted and the import should come from `@ngcompass/engine`.

### CI-2 — `resolveWorkerPath()` Duplicated
The worker path resolution logic appears in:
1. `packages/engine/src/worker-pool.ts`
2. `packages/planner/src/builder.ts`

Both probe a list of candidate file paths in the same order. Any change to worker path conventions requires updating two files.

### CI-3 — AST Walker Duplicated
The iterative DFS AST walker appears in:
1. `packages/ast/src/visitor.ts` (canonical, exported)
2. `packages/rules/src/visitor.ts` (copy)

### TICKET-009 — Fix `groupFailuresByFile` O(n²) array allocation in reporters

**Priority:** Medium
**Package:** `@ngcompass/reporters`
**Type:** Performance

**Description:**
`console-reporter.ts` lines 110–114: `reduce` with spread `[...existing, failure]` creates a new array for every failure processed. For files with many violations this is quadratic in memory allocations.

**Fix:**
```typescript
function groupFailuresByFile(failures: readonly RuleFailure[], cwd: string): Map<string, RuleFailure[]> {
    const map = new Map<string, RuleFailure[]>();
    for (const failure of failures) {
        const relativePath = path.relative(cwd, failure.filePath);
        const existing = map.get(relativePath);
        if (existing) {
            existing.push(failure);
        } else {
            map.set(relativePath, [failure]);
        }
    }
    return map;
}
```

**Acceptance Criteria:**
- [ ] No spread inside the grouping loop
- [ ] Memory usage is O(n) not O(n²) for the grouping operation
- [ ] Existing tests pass
