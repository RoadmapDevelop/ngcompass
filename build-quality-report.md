## 2. CI Workflow Audit

### BQ-CI-01: Trigger Branch Mismatch (Critical)

**File:** `.github/workflows/ci.yml`

```yaml
on:
  push:
    branches: [master, develop]    ← ⚠️ 'master' does not exist
  pull_request:
    branches: [master, develop]
```

The repository uses `main` as its default branch (confirmed by `.changeset/config.json`: `"baseBranch": "main"`). The `ci.yml` workflow triggers on `master` which **does not exist**. This means:

- **No CI runs on pushes to `main`** — the most critical protection is absent.
- The workflow only runs on `develop` pushes/PRs.
- Every merge to `main` goes unvalidated by `ci.yml`.

**Fix:** Change `branches: [master, develop]` → `branches: [main, develop]` in both push and pull_request triggers.

---

### BQ-CI-02: pnpm Version Mismatch (Critical)

**File:** `.github/workflows/test.yml`

```yaml
- uses: pnpm/action-setup@v2
  with:
    version: 8    ← ⚠️ root packageManager is pnpm@10.26.0
```

Root `package.json` declares `"packageManager": "pnpm@10.26.0"`. pnpm 8 uses a different lockfile format than pnpm 10. Running `pnpm install` with pnpm 8 against a `pnpm-lock.yaml` generated by pnpm 10 will:

1. **Fail** with a lockfile format error, OR
2. **Silently regenerate** the lockfile in the old format, causing non-reproducible installs.

In either case, CI results from `test.yml` are **unreliable** until this is fixed.

**Fix:** In `test.yml`, remove the explicit `version: 8` field. With pnpm 9+, `pnpm/action-setup@v2` (or `@v4`) reads the `packageManager` field from root `package.json` and installs the correct version automatically.

```yaml
- uses: pnpm/action-setup@v4   # reads packageManager field
```

### BQ-CI-03: Missing check-coverage.js Script (Critical)

**File:** `.github/workflows/test.yml`

```yaml
- name: Check coverage thresholds
  run: node scripts/check-coverage.js
```

The file `scripts/check-coverage.js` **does not exist** in the repository. This CI step will always fail with `Error: Cannot find module '...check-coverage.js'`. The workflow is broken for any run that reaches this step.

**Immediate fix:** Either create the script or remove the step and rely on vitest's built-in `--coverage.thresholds` (already configured in `vitest.config.ts`).

**Script to create** (minimal implementation):
```javascript
// scripts/check-coverage.js
import { readFileSync } from 'node:fs';
const summary = JSON.parse(readFileSync('coverage/coverage-summary.json', 'utf8'));
const total = summary.total;
const thresholds = { lines: 90, functions: 90, branches: 85, statements: 90 };
let failed = false;
for (const [key, min] of Object.entries(thresholds)) {
    const pct = total[key]?.pct ?? 0;
    if (pct < min) {
        console.error(`Coverage threshold failed: ${key} ${pct}% < ${min}%`);
        failed = true;
    }
}
if (failed) process.exit(1);
```

### BQ-CI-04: No Turbo in CI Pipelines

Both `ci.yml` and `test.yml` run raw pnpm scripts:

```yaml
- run: pnpm lint
- run: pnpm typecheck
- run: pnpm test:coverage
- run: pnpm build
```

These run sequentially and do not leverage Turbo's:
- **Parallel execution** (lint and test could run in parallel)
- **Remote cache** (Turbo remote cache is configured via `turbo.json` `"remoteCache": { "enabled": true }`)
- **Incremental build** (`^build` dependency chain means only changed packages rebuild)

This means every CI run does a full rebuild/retest of all 6 packages regardless of what changed.

**Fix:** Replace sequential `pnpm` calls with a single Turbo command:

```yaml
- run: pnpm exec turbo build lint typecheck test --concurrency=4
  env:
    TURBO_TOKEN: ${{ secrets.TURBO_TOKEN }}
    TURBO_TEAM: ${{ secrets.TURBO_TEAM }}
```

With remote cache warmed on main, feature branch CI runs will take seconds for unaffected packages.

**Estimated CI time improvement:** 40–60% reduction for typical feature branches touching 1–2 packages.

### BQ-CI-05: Overlapping Workflows with Different Matrix Configurations

`ci.yml` tests on Node 18.x, 20.x.
`test.yml` tests on Node 18.x, 20.x, **22.x**.

Both workflows trigger on `develop`. On a PR to `develop`, both workflows run — doubling CI minutes while providing nearly identical coverage. Neither provides full protection on `main` (see BQ-CI-01).

**Fix:**
1. Consolidate into a single `.github/workflows/ci.yml`.
2. Use one matrix: `[18.x, 20.x, 22.x]`.
3. Fix branch triggers to include `main`.
4. Delete the redundant `test.yml`.

## 3. Build Pipeline Analysis (Turbo)

### What's Working Well

The `turbo.json` pipeline is well-designed:

```json
"build": {
    "dependsOn": ["^build"],        // respects topological order
    "outputs": ["dist/**", ".turbo/**"],
    "inputs": ["src/**/*.ts", "package.json", "tsconfig.json"],
    "outputLogs": "new-only"
}
```

- **Correct topological ordering:** `^build` ensures `common` builds before `core`, `core` before `reporters`/`rules`, etc.
- **Fine-grained inputs:** Only `src/` and config changes invalidate the cache, not test files.
- **Separate `build:prod`** task for production (minification) vs development builds.
- **Remote cache configured** (`"remoteCache": { "enabled": true }`).

### BQ-TURBO-01: globalDependencies Include Runtime Files

```json
"globalDependencies": [".swcrc", "tsup.config.ts", "tsconfig.json"]
```

`.swcrc` and `tsup.config.ts` at root affect all builds — they are correctly listed as global dependencies. However, `tsup.config.ts` is the shared config factory that no package currently uses (see below). Its hash will still invalidate all task caches when it changes, even though the change has no effect.

**Fix:** After verifying that `tsup.config.ts` is truly unused (DEP-03 level cleanup), either remove it from `globalDependencies` or start actually using it in packages (preferred — see BQ-BUILD-02).

### BQ-TURBO-02: test Task Depends on `^build`, Not `^typecheck`

```json
"test": { "dependsOn": ["^build"] }
```

Tests require upstream packages to be built (so imports resolve from `dist/`). This is correct for integration tests. For pure unit tests that use vitest with SWC transforms (which don't need `dist/`), this creates unnecessary build wait times.

**Consider:** A `test:unit` task that only depends on `^typecheck` (much faster), while keeping `test:integration` depending on `^build`.

## 4. TypeScript Configuration Quality

### Three Configuration Strategies in One Repo

| Config file | module | moduleResolution | composite | Usage |
|------------|--------|-----------------|-----------|-------|
| `tsconfig.json` (root) | `Node16` | `Node16` | `true` | Used by root `typecheck` script and some tools |
| per-package `tsconfig.json` | `esnext` | `bundler` | `false` | Used by tsup/vitest compilation |
| `tsconfig.spec.json` | `commonjs` | `node` | — | Legacy ts-jest config (should be deleted) |

This inconsistency means:
1. The root `typecheck` (`turbo typecheck`) and the per-package `tsc --noEmit` use different module resolution.
2. A type error that appears in `bundler` resolution may not appear in `Node16` resolution and vice versa.
3. `tsconfig.spec.json` with `module: commonjs` is a legacy artifact from the old jest setup — it should be deleted.

### BQ-TS-01: Project References Disabled

Root `tsconfig.json` declares `"composite": true` and `"incremental": true`, implying TypeScript project references are intended. However, all package-level configs set `"composite": false` and `"incremental": false`, effectively disabling project references.

**Consequence:** `tsc --build` at root cannot leverage incremental compilation or reference graph validation. Each package is compiled in isolation without TypeScript knowing about dependencies between them.

**Fix:** Either commit to project references (set `composite: true` in all packages, add `"references"` arrays) or remove `composite: true` / `incremental: true` from root to eliminate the misleading implication.

### BQ-TS-02: cli Deviates in lib Setting

`packages/cli/tsconfig.json` sets `"lib": ["ESNext"]` while all others inherit `"lib": ["ES2022"]` from root. `ESNext` is a moving target that can cause API availability discrepancies across TS versions. There is no documented reason for this deviation.

**Fix:** Remove `"lib": ["ESNext"]` from `cli/tsconfig.json` to inherit the root `"lib": ["ES2022"]`.

### BQ-TS-03: Stale Include Paths in core and rules tsconfigs

See BV-01 in `boundary-violations.md`. Summary:
- `core/tsconfig.json` explicitly includes two non-existent `.ts` file paths
- `rules/tsconfig.json` includes a non-existent cross-package `../core/src/rules/domains` path

These are dead weight that will cause confusion during any future refactor.

## 5. Build Output & Package Quality

### BQ-BUILD-01: Missing `sideEffects` Declaration on All Packages

| Package | `sideEffects` field | Issue |
|---------|--------------------| ------|
| `common` | missing | Low risk — no side effects in source |
| `core` | missing | **High risk** — `import './rules/register-all.js'` is a real side effect |
| `reporters` | missing | Low risk |
| `rules` | missing | Low risk |
| `cli` | missing | Acceptable — CLI binaries are not bundled for tree-shaking |
| `testing` | missing | Low risk |

Without `sideEffects`, bundlers either:
- Keep all imports (safe but bloated), OR
- Drop side-effectful imports (can break rule registration silently)

**Fix:** After resolving BV-03 (remove `register-all.js` side effect from core barrel):
```json
// packages/core/package.json
{ "sideEffects": false }
```

For packages with known side effects, be explicit:
```json
{ "sideEffects": ["./dist/rules/register-all.js"] }
```

### BQ-BUILD-02: Shared tsup.config.ts Factory Completely Unused

`tsup.config.ts` at root exports a `createConfig({ entry, external, format })` factory intended to be imported by each package's build script. **Zero packages import it.** Each package runs tsup directly via inline command-line flags:

```json
"build": "tsup src/index.ts --format cjs,esm --dts --clean"
```

Consequences:
1. Inconsistent tsup options across packages (some have `--external typescript`, some don't).
2. Build configuration drift — future tsup option additions (e.g., `--shims`, `--treeshake`) must be manually applied to 6+ command strings.
3. Turbo marks the root `tsup.config.ts` as a `globalDependency`, polluting cache hashes for a file that has no effect on builds.

**Fix:** Adopt the shared factory:
```typescript
// packages/core/tsup.config.ts
import { createConfig } from '../../tsup.config.ts';
export default createConfig({
    entry: ['src/index.ts', 'src/planner/worker.ts', 'src/engine/execution-worker.ts'],
    external: ['@ngcompass/common', 'typescript']
});
```

Or simplify: standardize all build scripts on a single inline template and delete the unused factory.

### BQ-BUILD-03: Multiple Entry Points in Core and CLI Not Reflected in Exports Map

`@ngcompass/core` builds three entry points:
- `src/index.ts` → `dist/index.{js,cjs}`
- `src/planner/worker.ts` → (worker thread file)
- `src/engine/execution-worker.ts` → (worker thread file)

But `exports` only declares `.`:
```json
"exports": { ".": { ... } }
```

The worker files (`dist/planner/worker.js`, `dist/engine/execution-worker.js`) are loaded dynamically via `worker_threads` and do not need public exports. However, they should be declared in `exports` with a restricted path if they need to be addressable as package-internal paths:

```json
"exports": {
    ".": { "types": "...", "import": "...", "require": "..." },
    "./planner/worker": { "import": "./dist/planner/worker.js" },
    "./engine/execution-worker": { "import": "./dist/engine/execution-worker.js" }
}
```

Without this, the worker files can only be loaded via internal path resolution, which may fail in some bundler/deployment scenarios.

## 6. Test Infrastructure Quality

### BQ-TEST-01: Mixed File Extensions

| Package | Extension used |
|---------|---------------|
| `core`, `common`, `cli`, `rules` | `.test.ts` |
| `reporters` | `.spec.ts` |

Vitest handles both, but the inconsistency:
- Breaks grep-based tooling that searches for `*.test.ts`
- The root `vitest.config.ts` coverage config excludes both `**/*.test.ts` and `**/*.spec.ts` — so coverage exclusions work, but the inconsistency is still a friction source.

**Fix:** Standardize all test files to `.test.ts`. Rename the 3 `reporters` spec files.

### BQ-TEST-02: Stubs Have No Tests

`@ngcompass/testing/tests/` — no test files found.
`@ngcompass/rules/tests/` — only `setup.test.ts` (smoke test: `expect(rules).toBeDefined()`).

These packages provide no value and contribute to the 90% threshold being trivially met for stub packages while real packages may be under-tested.

### BQ-TEST-03: ts-jest in devDependencies Conflicts with vitest Setup

`@ngcompass/common` has `ts-jest@^29.4.6` in devDependencies. `ts-jest` is not used anywhere in the workspace. Its presence alongside `@types/jest@^30.0.0` will cause TypeScript to see duplicate global type declarations (`describe`, `it`, `expect`) from both Jest and Vitest globals, potentially causing confusing typecheck errors.

**Fix:** See DG-R3 in `dependency-governance.md`.

### BQ-TEST-04: Coverage Configuration Excludes index.ts

```typescript
// vitest.config.ts
exclude: ['**/index.ts']
```

Barrel re-export files (`index.ts`) are excluded from coverage. For most packages this is fine — barrels are just re-exports. However, `@ngcompass/core/src/index.ts` contains the side-effect import `import './rules/register-all.js'` which **is** logic. Excluding it from coverage means the registration path is never tested in isolation.
